## 1. Masalah: Foto & Nama Pengirim Belum Tersedia di API

### 1.1 `GET /api/feedback/{id}/messages` — Field `sender_foto` belum ada

Saat ini setiap objek pesan di response hanya mengirimkan `sender_name`, **tidak ada `sender_foto`**. Hal ini menyebabkan avatar di setiap bubble chat tidak bisa ditampilkan.

Seperti yang sudah kami baca di laporan Backend sebelumnya, secara teknis data `foto` sudah ada — method `formatMessage()` di `FeedbackChatController.php` memang me-_load_ relasi `sender` yang berisi `foto`, namun objek tersebut dibuang dan hanya `sender_name` yang dikembalikan.

**Yang kami minta — tambahkan `sender_foto` di setiap objek pesan:**

```json
// GET /api/feedback/{id}/messages → data.messages[i]
{
  "id": 33,
  "feedback_id": 12,
  "sender_id": 1,
  "sender_type": "admin",
  "sender_name": "Budi Admin",
  "sender_foto": "https://domain.com/assets/image/customers/profile/budi.jpg",  ← BARU
  "message": "Mohon maaf, sedang kami cek.",
  "read_at": "2026-06-20 11:00:00",
  "created_at": "2026-06-20 11:00:00",
  "is_initial": false
}
```

Jika `foto` null atau kosong (admin tidak punya foto), kirimkan `null` — frontend sudah siap menangani fallback inisial nama.

---

### 1.2 `GET /api/feedback/{id}/messages` — Objek `feedback` belum ada data admin

Saat ini objek `feedback` di response hanya berisi data Customer:

```json
"feedback": {
  "id": 12,
  "id_user": 5,
  "customer_name": "Budi Santoso",  ← ada
  "kriteria": "Kurang",
  "status": "Dibalas",
  "created_at": "2026-06-20 10:00:00"
  // ← TIDAK ADA data admin
}
```

Kami perlu data **admin terakhir yang membalas** untuk ditampilkan di AppBar halaman chat (foto + nama lawan bicara). Ketika belum ada yang membalas, AppBar menampilkan _"Menunggu Admin Pembalas"_.

**Yang kami minta — tambahkan `last_admin_name` dan `last_admin_foto` di objek `feedback`:**

```json
"feedback": {
  "id": 12,
  "id_user": 5,
  "customer_name": "Budi Santoso",
  "kriteria": "Kurang",
  "status": "Dibalas",
  "created_at": "2026-06-20 10:00:00",
  "last_admin_name": "Budi Admin",          ← BARU (null jika belum ada yang balas)
  "last_admin_foto": "https://domain.com/assets/image/customers/profile/budi.jpg"  ← BARU (null jika belum ada)
}
```

> **Catatan:** `last_admin_name` dan `last_admin_foto` diisi dari pesan terakhir yang `sender_type = 'admin'`. Jika belum ada pesan admin sama sekali, kirimkan `null` — frontend akan tampilkan state "Menunggu".

### 1.3 `GET /api/feedback` (list) — `sender` di `latest_message` belum mengandung `foto`

Di list feedback, objek `latest_message.sender` saat ini hanya berisi `id` dan `name`. Kami perlu `foto` untuk menampilkan avatar admin di kartu percakapan list.

**Yang kami minta — tambahkan `foto` di objek `sender` dalam `latest_message`:**

```json
"latest_message": {
  "id": 40,
  "feedback_id": 12,
  "sender_id": 1,
  "sender_type": "admin",
  "message": "Halo, ada yang bisa dibantu?",
  "read_at": null,

    "id": 1,
    "name": "Budi Admin",
    "foto": "https://domain.com/assets/image/customers/profile/budi.jpg"  ← BARU
  }

```

## 2. Studi Kasus Multi-Admin — Arsitektur yang Kami Usulkan

Ini masalah desain yang perlu kami selaraskan bersama sebelum ada asumsi yang berbeda.

### Skenario

```
Customer A kirim feedback → masuk sebagai percakapan ID 12

Admin A membalas       → pesan masuk ke feedback_messages (sender_id=Admin A)
Admin B juga membalas  → pesan masuk ke feedback_messages (sender_id=Admin B)
```

### Pertanyaan: Apakah ini 1 thread atau 2 thread?

Menurut kami (dan sesuai struktur database yang sudah ada), **jawabannya adalah 1 thread** dengan banyak pengirim dari sisi admin. Artinya:

- `feedback_id = 12` tetap **satu thread tunggal**
- Di dalam thread tersebut bisa ada banyak pesan dari Admin A, Admin B, dst.
- Di sisi Mobile Customer, semua balasan dari semua admin muncul dalam **satu room chat yang sama** (mirip group dari sisi admin, tapi Customer hanya melihat 1 thread)
- Setiap pesan memiliki `sender_name` dan `sender_foto` **per pesan** — sehingga bubble Admin A dan Admin B akan terlihat berbeda (nama & avatar berbeda)

### Konsekuensi UI Mobile (sudah kami implementasikan)

```
[Room Chat Customer A — Feedback #12]
─────────────────────────────────
  📝 Feedback Awal: "Tenda telat..."     [Customer A]
        "Mohon maaf, sedang dicek"       [Admin A — foto & nama Admin A]
        "Sudah kami teruskan ke tim"     [Admin B — foto & nama Admin B]  ← berbeda!
  "Terima kasih info nya"                [Customer A]
─────────────────────────────────
```

**AppBar** menampilkan **admin terakhir yang membalas** (bukan admin pertama). Jadi jika Admin B terakhir membalas, AppBar menampilkan foto & nama Admin B.

### Yang TIDAK kami inginkan

❌ Membuat thread/feedback terpisah per admin — ini akan memperumit UX Customer yang harus buka banyak thread untuk satu keluhan

❌ Hardcode nama "Admin KampSewa" — Customer berhak tahu siapa yang membalas

### Yang perlu dikonfirmasi Backend

Apakah saat ini **satu feedback bisa dibalas oleh lebih dari 1 admin** melalui panel web? Jika ya, apakah ada **notifikasi ke admin lain** bahwa sudah ada yang membalas? Kami ingin tahu agar bisa adjust tampilan di Mobile.

# Report Permintaan: Perubahan Arsitektur Multi-Admin Chat

**Tanggal:** 29 September 2026
**Kepada:** Tim Backend
**Dari:** Tim Frontend / Mobile
**Perihal:** Permintaan Restrukturisasi Relasi Feedback & Chat Multi-Admin

Halo Tim Backend,

Saat ini kami menemukan sebuah isu kritikal pada pengalaman *Customer* di aplikasi Mobile ketika sebuah feedback dibalas oleh lebih dari satu admin. 

### Akar Masalah:
Secara arsitektur saat ini, semua balasan (dari berbagai admin) disatukan ke dalam satu `feedback_id` yang sama di dalam tabel `feedback_messages`. Akibatnya, ketika Admin B ikut membalas, Mobile (yang mengambil `last_admin_name`) akan seketika menimpa nama Admin A menjadi Admin B. Percakapan menjadi campur aduk dan membingungkan *Customer*.

### Kebutuhan (Solusi yang Diharapkan):
*Customer* seharusnya melihat **2 chat/room yang terpisah** jika ada 2 admin yang berbeda merespons feedback yang sama.

Untuk mengakomodasi ini, kami mengusulkan perubahan di sisi Backend:

1. **Pembuatan Konsep `Room Chat` / `Thread`**:
   Satu Feedback (dari Customer) bisa memiliki banyak *Room* (satu *room* per Admin yang merespons).
   - Tabel `feedback_messages` perlu ditambahkan kolom `admin_id` (atau `room_id`), sehingga pesan dari *Customer* bisa terhubung ke obrolan dengan *Admin* yang tepat.

2. **Perubahan API `GET /api/feedback` (List Chat)**:
   List API tidak lagi sekadar mengembalikan list *Feedback*, melainkan **List Room Chat**. Jika ada 2 admin membalas 1 feedback, API list harus mengembalikan 2 objek *room* yang berbeda (misalnya "Chat dengan Admin A" dan "Chat dengan Admin B").

3. **Perubahan API `GET /api/feedback/{id}/messages`**:
   API *detail message* tidak bisa lagi hanya memakai `feedback_id`. Kami butuh parameter tambahan, misal `GET /api/chat-room/{room_id}/messages`, agar Mobile hanya me-*render* pesan antara *Customer* tersebut dengan satu *Admin* tertentu.

**Catatan Tambahan**:
Untuk sementara waktu, sebagai *quick fix*, fitur chat di **sisi Admin Web** sudah difilter agar setiap Admin **hanya** melihat chat dari *Customer* dan pesan dari dirinya sendiri (balasan dari Admin lain disembunyikan dari layar miliknya).

Mohon segera direview dan diagendakan untuk perubahan skema database ini agar kami bisa menyesuaikan *UI Mobile* secepatnya.

Terima kasih.

### Perubahan Database:
Tabel `feedback_messages` sekarang memiliki kolom baru `admin_id`. Kolom ini berfungsi sebagai relasi untuk mengetahui *Admin* mana yang menjadi lawan bicara, terutama saat Customer membalas pesan. **(Info untuk Tim Developer: Jalankan `php artisan migrate` untuk menerapkan perubahan skema ini di lokal Anda).**

### Perubahan Endpoint API (Mobile):

**1. GET /api/chat-room**
Digunakan untuk mendapatkan daftar *Room Chat* (pengganti `/api/feedback`).
- Jika sebuah feedback dibalas oleh 2 Admin, API ini akan mereturn 2 *room* yang berbeda.
- Response sekarang menyertakan atribut `room_id` (berformat `feedback_id-admin_id`) dan `admin_id`.

**2. GET /api/chat-room/{feedback_id}/{admin_id}/messages**
Mengambil detail pesan hanya antara Customer dengan satu Admin tertentu.
- Format *response*-nya sama dengan sebelumnya, tetapi difilter secara ketat.

**3. POST /api/chat-room/{feedback_id}/{admin_id}/messages**
Digunakan ketika Customer membalas chat.
- Param `admin_id` diperlukan agar pesan bisa tersambung ke layar Admin yang tepat di Web.

Silakan pelajari *endpoint* baru ini dan mulai sesuaikan UI Mobile menjadi struktur 2-*room* (atau lebih) seperti yang direncanakan. Jika ada hal yang belum *clear*, *feel free* untuk berdiskusi dengan kami!

# Report Bug: API /api/chat-room Masih Grouping Berdasarkan Feedback ID

**Tanggal:** 29 September 2026
**Kepada:** Tim Backend
**Dari:** Tim Frontend / Mobile
**Perihal:** List Chat Menimpa Admin Sebelumnya Saat Ada 2 Admin Membalas

Halo Tim Backend,

Kami menemukan *critical bug* pada saat melakukan testing *end-to-end* untuk fitur Multi-Room Chat yang baru saja diimplementasikan.

### Skenario Bug:
1. Customer mengirim feedback.
2. Admin A membalas. Di aplikasi Mobile, muncul 1 kartu chat dengan Admin A.
3. Admin B kemudian ikut membalas feedback yang sama.
4. Di aplikasi Mobile, bukannya muncul 2 kartu chat terpisah, **kartu Admin A malah berubah menjadi kartu Admin B**.
5. Saat chat tersebut dibuka, Customer hanya melihat *history* obrolannya dengan Admin B. *History* dengan Admin A hilang/tidak bisa diakses lagi oleh Customer karena kartunya tertimpa.

### Analisis Akar Masalah:
Berdasarkan investigasi dari sisi Mobile (Flutter), aplikasi kami hanya menampilkan list JSON *plek-ketiplek* sesuai apa yang dikembalikan oleh API `GET /api/chat-room`. 

Artinya, **API `GET /api/chat-room` saat ini masih mereturn 1 objek per `feedback_id`** (kemungkinan API masih melakukan `GROUP BY feedback_id` atau hanya mengambil `admin_id` dari pesan yang paling terakhir masuk ke tabel `feedback_messages`).

### Solusi yang Diperlukan:
Agar fitur Multi-Room ini benar-benar berjalan, konsep "List" tidak boleh lagi berbasis `feedback_id`, melainkan berbasis **`room_id`** (kombinasi `feedback_id` + `admin_id`). 

Mohon perbaiki *query* SQL di *endpoint* `GET /api/chat-room` dengan logika sebagai berikut:
- Harus melakukan `GROUP BY feedback_id, admin_id` (khusus untuk pesan-pesan yang ada `admin_id`-nya).
- Jika sebuah feedback (ID: 12) dibalas oleh Admin A (ID: 5) dan Admin B (ID: 6), maka array `data` yang direturn **wajib** berisi 2 JSON object yang terpisah:
  1. Object dengan `id: 12`, `admin_id: 5`
  2. Object dengan `id: 12`, `admin_id: 6`

Dengan begitu, Mobile akan langsung me-render 2 kartu obrolan di layar Customer, dan masing-masing kartu akan mengarah ke `GET /api/chat-room/12/5/messages` dan `GET /api/chat-room/12/6/messages`.

Tolong segera diperbaiki dari sisi *query* Backend-nya ya tim, karena di sisi Mobile arsitekturnya sudah siap menerima list ganda seperti skema di atas.

Terima kasih!

# Report Bug: Pesan Masuk ke Admin yang Salah & Fallback Info Admin

**Tanggal:** 29 September 2026
**Kepada:** Tim Backend
**Dari:** Tim Frontend / Mobile
**Perihal:** Bug pada proses Reply Customer & Kebutuhan Root Info Admin

Halo Tim Backend,

Terima kasih atas update sebelumnya yang merubah API `/api/chat-room` dengan `id` berformat `feedback_id-admin_id`. Di sisi Frontend (Flutter), kami sudah menyesuaikannya dan kartu chat kini sudah muncul terpisah tanpa *overlap*.

Namun, ada 2 *bug critical* baru yang terjadi ketika digunakan:

### 1. Pesan Customer Nyasar (Cross-Admin Bug)
**Masalah:** 
Saat Customer mengklik kartu Admin A (artinya Mobile mengirim `POST /api/chat-room/{feedback_id}/{admin_id_A}/messages`), balasan dari Customer tersebut **malah masuk/tersimpan untuk Admin B**.
**Analisis Frontend:**
Di aplikasi Mobile, kami sudah memastikan *body request* dan URL parameter yang kami tembak adalah tepat untuk Admin A (misal: `/api/chat-room/12/5/messages`). Tapi data malah tersimpan untuk Admin dengan ID 6 (Admin B).
**Solusi Backend yang Diperlukan:**
Tolong pastikan *controller/logic* saat memproses `POST` balasan *Customer* benar-benar menggunakan `$admin_id` yang diterima dari parameter URL (atau dari *body* request), dan **JANGAN** mengambil `admin_id` dari kueri seperti `FeedbackMessage::latest()->first()->sender_id` yang akan selalu mengambil admin terakhir yang membalas siapapun itu.

### 2. Nama & Foto Admin Hilang Saat Customer Membalas
**Masalah:**
Saat ini, jika Admin yang merespons terakhir kali, nama dan fotonya muncul di UI Mobile. TAPI, saat Customer *membalas balik* pesan admin tersebut, data Admin di list UI langsung berubah menjadi **"Menunggu Admin Pembalas"**.
**Analisis Frontend:**
Berdasarkan info dari kalian sebelumnya, info admin disisipkan di dalam objek `latest_message`. Ketika Customer yang membalas terakhir, objek `latest_message` tentu saja berisi info Customer. Akibatnya, Mobile kehilangan data nama dan foto Admin lawan bicaranya pada *room* tersebut.
**Solusi Backend yang Diperlukan:**
Agar setiap *Room* konsisten, **mohon sertakan objek `admin` (atau field `last_admin_name` dan `last_admin_foto`) di level *root* respons `GET /api/chat-room`** (bukan sekadar nempel di dalam `latest_message`).
Contoh bentuk JSON yang benar per *item*:
```json
{
  "id": "12-5",
  "feedback_id": 12,
  "admin_id": 5,
  "last_admin_name": "Budi Admin", 
  "last_admin_foto": "budi.jpg",
  "latest_message": { "sender_type": "customer", "message": "Siap!" }
}
```
Atau cukup:
```json
{
  "id": "12-5",
  "feedback_id": 12,
  "admin_id": 5,
  "admin": { "name": "Budi Admin", "foto": "budi.jpg" },
  "latest_message": { ... }
}
```
Jika format tersebut dikembalikan, Mobile akan otomatis mempertahankan nama dan foto Admin secara paten walaupun pesan terakhirnya dikirim oleh Customer.

Mohon bantuannya untuk diperbaiki dari sisi *Server*.

Terima kasih.
