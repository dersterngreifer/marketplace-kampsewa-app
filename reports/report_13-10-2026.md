# Report Implementasi Fitur Iklan Mitra & Sistem Diskon Produk (Promosi Toko)
**Tanggal**: 13-10-2026

---

## 1. Konteks & Ringkasan Pembaruan

Menjawab kebutuhan integrasi antara aplikasi mobile Flutter KampSewa dengan Backend dan Web Mitra mengenai standarisasi banner iklan rasio 16:9, sistem promosi diskon toko (*store-wide* dan *selected products*), serta filter/sorting produk di profil toko publik, telah dilakukan implementasi menyeluruh pada arsitektur database, layanan backend, endpoint API, dan dashboard web mitra.

Pembaruan utama yang telah diselesaikan:
1. **Migrasi Skema Database**: Penyesuaian tabel `iklan` serta pembuatan tabel baru `promosi_toko` dan `promosi_produk`.
2. **Service Kalkulasi Diskon Otomatis (`PromoService`)**: Menghitung harga sewa efektif (`harga`), harga asli dicoret (`harga_asli`), persentase diskon (`persentase_diskon`), potongan nominal (`potongan_harga`), dan label promo aktif (`nama_promo`) dengan query batch efisien (anti N+1).
3. **Pembaruan API Iklan Dashboard (`GET /api/iklan`)**: Menghubungkan banner iklan secara dinamis ke toko mitra (`id_toko`), produk terkait (`id_produk`), deskripsi utuh untuk popup bottom sheet, badge promo, dan flag diskon aktif (`has_active_discount`).
4. **Pembaruan API Toko Publik (`GET /api/store/{id_user}` & `GET /api/store/{id_user}/products`)**:
   - Menambahkan metadata `active_promo` pada profil toko publik.
   - Menambahkan fitur query sorting (`sort=discount_desc|discount_asc|price_asc|price_desc|latest`) dan filtering produk promo (`is_promo=1`).
5. **Pembaruan Seluruh Endpoint Produk**: Menjamin field kalkulasi diskon (`is_diskon`, `harga_asli`, `harga`, `persentase_diskon`, `potongan_harga`, `nama_promo`) otomatis tersedia di beranda, rekomendasi pencarian, katalog kategori, detail produk, dan keranjang.
6. **API Manajemen Promo Mitra (`/api/mitra/promo`)**: Menyediakan RESTful API lengkap bagi mitra untuk mengelola program diskon toko.
7. **Modul Dashboard Web Mitra (Promo & Campaign Manager)**: Halaman web lengkap bagi mitra untuk membuat, mengedit, mengunggah banner 16:9, memilih produk spesifik via tabel checklist interaktif, serta mengaktifkan/menonaktifkan promo.

## 2. Skema Database yang Telah Diimplementasikan

### A. Tabel `iklan` (Kolom Tambahan)
- `id_produk` (`unsignedBigInteger`, nullable, foreign key ke `produk.id` ON DELETE SET NULL).
- `target_type` (`varchar(20)`, default `'store'`) — nilai: `'store'`, `'product'`, `'external'`.
- `badge_promo` (`varchar(50)`, nullable) — contoh: `"DISKON 20%"`, `"FLASH SALE"`.
- `tanggal_mulai` (`datetime`, nullable).
- `tanggal_selesai` (`datetime`, nullable).
- `status` (`enum('active','inactive','expired')`, default `'active'`).

### B. Tabel Baru: `promosi_toko`
```sql
CREATE TABLE promosi_toko (
    id_promo BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    id_user BIGINT UNSIGNED NOT NULL,
    judul_promo VARCHAR(150) NOT NULL,
    deskripsi_promo TEXT NULL,
    poster VARCHAR(255) NULL,
    tipe_diskon ENUM('persen', 'nominal') DEFAULT 'persen',
    nilai_diskon DECIMAL(10,2) NOT NULL,
    cakupan ENUM('all_products', 'selected_products') DEFAULT 'all_products',
    tanggal_mulai DATETIME NOT NULL,
    tanggal_selesai DATETIME NOT NULL,
    is_banner BOOLEAN DEFAULT FALSE,
    is_active BOOLEAN DEFAULT TRUE,
    status ENUM('active', 'draft', 'inactive') DEFAULT 'active',
    created_at TIMESTAMP NULL,
    updated_at TIMESTAMP NULL,
    FOREIGN KEY (id_user) REFERENCES users(id) ON DELETE CASCADE
);
```

### C. Tabel Relasi: `promosi_produk`
```sql
CREATE TABLE promosi_produk (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    id_promo BIGINT UNSIGNED NOT NULL,
    id_produk BIGINT UNSIGNED NOT NULL,
    created_at TIMESTAMP NULL,
    updated_at TIMESTAMP NULL,
    FOREIGN KEY (id_promo) REFERENCES promosi_toko(id_promo) ON DELETE CASCADE,
    FOREIGN KEY (id_produk) REFERENCES produk(id) ON DELETE CASCADE,
    UNIQUE KEY unique_promo_produk (id_promo, id_produk)
);
```

# Report Perbaikan Fitur Metode Pembayaran / Transfer Toko Mitra (`GET /api/transaksi/bank-toko`)
**Tanggal**: 13-10-2026 (Pembaruan Isolasi Data Rekening Bank Toko Berdasarkan User Login)

---

## 1. Latar Belakang Masalah (Root Cause Analysis)

Pada halaman pendaftaran/pengaturan toko mitra mobile (`LayoutTambahDataToko` dan `LayoutTambahMetodeTransfer`), ditemukan permasalahan daftar metode transfer bank menampilkan banyak sekali rekening bank secara otomatis, padahal user yang sedang login belum memilih atau menambahkan rekening bank miliknya.

Setelah dilakukan penelusuran menyeluruh antara Frontend Mobile Flutter dan Backend Laravel, ditemukan dua penyebab utama:

1. **Bug Query Parameter Dio (Frontend Mobile Flutter)**:
   - Pada method `apiTransaksi.getBankOpsiPembayaran(context, idStr)`, Flutter melakukan HTTP request dengan method `GET`:
     ```dart
     Map body = {'id_user': idToko};
     final response = await dio.get(url, data: body, ...);
     ```
   - Dio mengirim `{'id_user': idToko}` di dalam **HTTP Request Body** (`data: body`), bukan sebagai **URL Query Parameter** (`queryParameters: {'id_user': idToko}`).
   - Protokol HTTP GET standarnya tidak menggunakan message body, sehingga Laravel tidak membaca isi body GET request pada pemanggilan `$request->query('id_user')`. Akibatnya, nilai `$id_user` di sisi backend selalu terbaca `NULL`.

2. **Celah Filter Query pada Controller Backend (`TransaksiController@bankToko`)**:
   - Kode awal pada `TransaksiController.php`:
     ```php
     $id_user = request()->query('id_user');
     $name_store = request()->query('name_store');

     $bank = Bank::select('bank.id', 'bank.id_user', 'bank.rekening', DB::raw('UPPER(bank.bank) as bank'))
         ->where(function ($query) use ($id_user, $name_store) {
             if ($id_user) {
                 $query->where('id_user', $id_user);
             }
             if ($name_store) {
                 $query->orWhere('name_store', $name_store);
             }
         })
         ->get();
     ```
   - Ketika `$id_user` bernilai `null` dan `$name_store` bernilai `null`, blok `where()` di atas tidak memiliki kondisi filter sama sekali!
   - Akibatnya, query yang dieksekusi adalah `SELECT ... FROM bank`, yang mengekstrak **seluruh data rekening bank milik SEMUA pengguna di tabel database** tanpa filter.
   - Selain itu, tabel `bank` tidak memiliki kolom `name_store`, sehingga pemanggilan `orWhere('name_store', ...)` pada tabel `bank` akan menghasilkan error `Column not found` jika `name_store` dikirim.

---

## 2. Solusi & Perbaikan yang Telah Diimplementasikan

### A. Perbaikan Sisi Backend (`marketplace-kampsewa-web`)
1. **Perbaikan Keamanan & Logika Filter (`TransaksiController@bankToko`)**:
   - Mendukung pembacaan parameter dari query string maupun request input: `request()->query('id_user') ?? request()->input('id_user')`.
   - Menambahkan fallback autentikasi token Bearer Sanctum jika `id_user` tidak dikirim: `auth('sanctum')->id()`.
   - **Isolasi Data**: Jika `id_user` dan `name_store` tidak ditemukan, backend **TIDAK AKAN** membuang seluruh isi tabel `bank`, melainkan mengembalikan array kosong `[]`:
     ```php
     if (!$id_user && !$name_store) {
         return response()->json([
             'message' => 'success',
             'bank' => [],
         ]);
     }
     ```
   - Filter `name_store` diperbaiki dengan relasi `whereHas('user', ...)` karena kolom `name_store` berada pada tabel `users`.
2. **Penambahan Relasi pada Model `Bank.php`**:
   - Menambahkan method relasi `public function user() { return $this->belongsTo(User::class, 'id_user'); }`.

### B. Perbaikan Sisi Frontend Mobile Flutter (`marketplace-kampsewa-app`)
1. **Standarisasi Query Parameter (`ApiTransaksi@getBankOpsiPembayaran`)**:
   - Mengubah pemanggilan `dio.get` dari `data: body` menjadi `queryParameters: {'id_user': idToko}`.
   - Endpoint sekarang memanggil `GET /api/transaksi/bank-toko?id_user={id_user}` secara valid dan presisi.
2. **Pembersihan Cache State (`LayoutTambahDataToko`)**:
   - Membersihkan list reaktif `apiTransaksi.listBankMetodeBayar.clear()` sebelum memanggil endpoint agar tidak ada sisa data sesi/toko lain.
   - Menambahkan kotak informasi *empty state* yang informatif jika toko belum memiliki rekening transfer (`"Belum ada metode transfer bank. Klik '+ Tambah' untuk menambahkan rekening toko Anda."`).
3. **Inisialisasi Form Input (`LayoutTambahMetodeTransfer`)**:
   - Menambahkan `initState()` agar saat mode edit (`edit == true`), field *No Rekening* dan *Jenis Bank* langsung terisi data rekening yang dipilih.
   - Mengosongkan controller saat mode tambah baru (`edit == false`).
4. **Penyempurnaan Endpoint & Autentikasi (`ApiDataUser`)**:
   - Menambahkan endpoint `updateBankMetodeTransfer` (`/api/user/update-bank/`) dan `deleteBankMetodeTransfer` (`/api/user/delete-bank/`) pada `ApiEndpoints`.
   - Melengkapi header `Authorization: Bearer $token`, `baseUrl`, dan path parameter `$bankId` pada method `updateBankMetodeTransfer` dan `deleteBankMetodeTransfer`.

# Report Evaluasi & Penyesuaian Endpoint Statistik Pesanan User Mobile (`GET /api/statistik-pesanan/{id_user}`)

## 1. Analisis Permasalahan & Temuan Lapangan (Root Cause Analysis)

Setelah dilakukan audit komprehensif antara UI Profil Mobile Flutter (`LayoutProfile`), service API mobile (`api_data_user.dart`), Controller Backend (`ChartWebController@apiStatistikPesanan`), dan data riil di tabel database `penyewaan` & `detail_penyewaan`, ditemukan beberapa permasalahan kritis yang menyebabkan angka statistik (*Total Pesanan*, *Pesanan Pending*, *Sedang Disewa*, *Produk Pending*) **TIDAK SESUAI / BERNILAI 0**:

### A. Salah Target Filter User ID (`produk.id_user` vs `penyewaan.id_user`)
- **Fakta Skema Database**:
  - Kolom `penyewaan.id_user` adalah foreign key ke `users.id` yang merepresentasikan **Penyewa / Pelanggan (Customer)** pembuat order sewa.
  - Kolom `produk.id_user` adalah foreign key ke `users.id` yang merepresentasikan **Mitra Toko Pemilik Barang**.
- **Celah Kode Backend Awal**:
  ```php
  $total_semua_pesanan = DB::table('penyewaan')
      ->join('detail_penyewaan', 'penyewaan.id', '=', 'detail_penyewaan.id_penyewaan')
      ->join('produk', 'detail_penyewaan.id_produk', '=', 'produk.id')
      ->where('produk.id_user', $id_user) // <-- HANYA MENGHITUNG JIKA USER MEMILIKI PRODUK TOKO!
      ...
  ```
- **Dampak Fatal**:
  Jika user yang sedang login di aplikasi mobile adalah **Customer biasa** (bukan toko atau belum mendaftarkan produk), maka query `WHERE produk.id_user = $id_user` akan **SELALU MENGHASILKAN 0** untuk semua metrik!
  Padahal pelanggan tersebut telah membuat transaksi penyewaan di tabel `penyewaan`. Di layar profil, semua angka statistik tampil 0.

### B. Mismatch Nilai Status Penyewaan (`Aktif` vs `berlangsung` & `Pending` vs `Pengambilan`)
- Berdasarkan pemeriksaan langsung terhadap 502 data di tabel `penyewaan`:
  - Status sewa berjalan tersimpan dengan nilai string **`'berlangsung'`** (sebanyak 150 transaksi) dan dalam varian lain `'Aktif'`.
  - Backend lama memfilter secara kaku dengan `where('penyewaan.status_penyewaan', 'Aktif')`. Akibatnya, seluruh 150 transaksi berstatus `'berlangsung'` tidak pernah terhitung (`Sedang Disewa: 0`).
  - Untuk status pending, pesanan yang telah dibayar namun menunggu serah terima unit / pengantaran berstatus `'Pengambilan'` tidak terhitung di kategori pending.

### C. Ketiadaan Pemisahan Konteks Role (Dual-Role Aware)
- Halaman profil mobile dapat dibuka oleh **Customer Biasa** maupun **Mitra Toko**.
- Mitra Toko membutuhkan visibilitas pesanan masuk tokonya, sedangkan Customer membutuhkan data transaksi sewa miliknya sendiri.
- Endpoint sebelumnya tidak memiliki mekanisme deteksi peran (*role detection*) maupun query parameter (`?role=customer` atau `?role=mitra`).

## 2. Solusi & Implementasi Teknis Backend

Telah dilakukan pembaruan dan pengoptimalan pada method `apiStatistikPesanan($id_user)` di Controller:
`App\Http\Controllers\Api\ChartWebController.php`

### Fitur Pembaruan:
1. **Perhitungan Mandiri untuk Customer**:
   - Menghitung transaksi langsung dari tabel `penyewaan` dengan filter `penyewaan.id_user = $id_user`.
   - Menggunakan query cepat dan efisien tanpa perlu join bertingkat untuk penghitungan jumlah order.
2. **Pencocokan Status Case-Insensitive & Multi-Status**:

   - `Pesanan Pending`: Mencakup status `'pending'` dan `'pengambilan'` via `LOWER(status_penyewaan) IN ('pending', 'pengambilan')`.
3. **Smart Auto-Detection & Dual-Role Support**:
   - Menerima parameter opsional: `?role=customer` atau `?role=mitra`.
   - Jika tanpa parameter query, sistem secara cerdas melakukan auto-detection:
     - Jika user adalah Mitra Aktif dengan pesanan toko masuk, menyajikan statistik toko.
     - Jika user adalah Customer biasa, menyajikan statistik transaksi sewa customer.
   - Respon JSON selalu menyertakan breakdown data lengkap `customer` dan `mitra` di dalam objek data.
