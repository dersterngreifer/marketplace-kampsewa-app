# Request Fitur Follow & Unfollow (Following & Followers)

Berdasarkan kebutuhan UI untuk fitur follow/unfollow di `layout_profile.dart` dan `layout_public_store_profile.dart`, berikut adalah request untuk tim Backend:

## 1. Penambahan Tabel Database
Dibutuhkan tabel baru (misalnya tabel `followers`) untuk menyimpan relasi follow antar user dengan struktur dasar:
- `id` (Primary Key)
- `follower_id` (ID user yang melakukan follow)
- `followed_id` (ID user yang di-follow)
- `created_at` (Timestamp)

## 2. Penyesuaian Response API Profile yang Sudah Ada
Untuk API Profile (Data User Sendiri) dan API Store Profile (Public Profile):
- Tambahkan field `total_followers` (Integer)
- Tambahkan field `total_following` (Integer)
- Tambahkan field `is_followed_by_me` (Boolean) -> Khusus untuk public profile, menandakan apakah user yang sedang login saat ini (current user) sudah mem-follow akun tersebut atau belum (digunakan untuk state tombol Ikuti/Mengikuti).

## 3. Pembuatan API Endpoint Baru
- **Endpoint Follow User**
  - `POST /api/follow/{user_id}`
  - Fungsi: Menyimpan data follow (current user mem-follow user_id).
- **Endpoint Unfollow User**
  - `POST /api/unfollow/{user_id}` atau `DELETE /api/follow/{user_id}`
  - Fungsi: Menghapus relasi follow.
- **Endpoint List Followers**
  - `GET /api/user/{user_id}/followers`
  - Fungsi: Menampilkan list user yang mem-follow `user_id`.
  - Response Data: List objek user (id, name, avatar/logo), beserta field `is_followed_by_me` (untuk tombol Ikuti/Mengikuti di dalam list).
- **Endpoint List Following**
  - `GET /api/user/{user_id}/following`
  - Fungsi: Menampilkan list user yang di-follow oleh `user_id`.
  - Response Data: List objek user (id, name, avatar/logo), beserta field `is_followed_by_me`.

*Catatan untuk integrasi Frontend:*
Di frontend, kami akan membuatkan halaman List Followers/Following. Jika dalam list tersebut terdapat akun current user (akun "Anda"), maka frontend akan melakukan sorting agar akun tersebut berada di urutan nomor satu dan diberikan UI/label khusus "Anda". Backend cukup memberikan list data user secara normal saja, pemilahan UI "Anda" akan di-handle oleh frontend berdasarkan pencocokan ID login saat ini.

## Update Format Response Public Store Profile (01-10-2026)
Untuk mengakomodir klik profile dari List Followers/Following ke halaman Public Profile, Endpoint `GET /api/store/{id_user}` harus dimodifikasi menjadi **Universal Profile** agar tidak error saat profil user biasa diakses.

**Detail Request Penyesuaian:**
- Jika `id_user` yang diminta adalah **bukan toko/mitra**:
  - Mohon **jangan** kembalikan error 404 / gagal.
  - Tetap kembalikan response Success 200, dengan me-mapping data user:
    - `nama_store` diisi dengan *nama lengkap user*.
    - `foto_toko` diisi dengan *foto profil user*.
    - Field stat produk (`rating_toko`, `total_produk_aktif`, `total_transaksi_selesai`, `total_ulasan`) diisi `0`.
- **Penambahan field baru:** Tambahkan parameter `is_toko` (boolean) di object response data toko.
  - `is_toko: true` = Frontend akan menampilkan stat lengkap beserta daftar produknya.
  - `is_toko: false` = Frontend akan menyembunyikan blok stat toko dan menonaktifkan pencarian produk, lalu menampilkan informasi bahwa "Pengguna ini adalah pengguna biasa dan tidak menyewakan produk".

## Revisi Logic URL Avatar pada API Followers & Following (01-10-2026)
Terdapat penyesuaian kebutuhan UI untuk foto profil yang ditampilkan di *List Followers/Following* (`GET /api/user/{user_id}/followers` dan `following`).

**Detail Request:**
Mohon ubah prioritas pengambilan URL gambar untuk field `avatar` menjadi seperti berikut:
1. Cek apakah user tersebut adalah mitra/toko (`is_toko == true` atau sejenisnya).
2. **Jika Toko**, prioritaskan menggunakan `foto_toko` (Logo Toko). Jika `foto_toko` null/kosong, baru *fallback* ke `foto` (Foto Profil Pribadi).
3. **Jika Bukan Toko** (User Biasa), gunakan `foto` (Foto Profil Pribadi).
4. Jika keduanya kosong, kembalikan `null`.

Tujuannya agar saat user melihat list followers/following, akun-akun yang merupakan toko bisa langsung dikenali melalui Logo Toko mereka, bukan sekadar foto profil pribadi.

## Request API Chat Antar Pengguna (User-to-User) (01-10-2026)
Berdasarkan kebutuhan fitur baru di aplikasi untuk mengakomodasi interaksi pesan (chat) antar pengguna (baik pengguna biasa maupun pengguna mitra/toko), berikut adalah request untuk tim Backend:

**1. Penambahan Struktur Database Chat**
Dibutuhkan tabel untuk menyimpan riwayat percakapan antar user, seperti `chat_rooms` dan `chat_messages`:
- `chat_rooms`: Menyimpan id room, user1_id, user2_id, last_message, dll.
- `chat_messages`: Menyimpan id pesan, room_id, sender_id, receiver_id, message_text, is_read (boolean), created_at.

**2. Pembuatan API Endpoint Baru**
- **Endpoint Get List Chat Rooms (Inbox)**
  - `GET /api/chat/rooms`
  - Fungsi: Mengambil daftar percakapan pengguna (current user).
  - Response Data: List objek room, meliputi info lawan bicara (nama, foto profil/toko), pesan terakhir, waktu pesan, dan **`unread_count`** (jumlah pesan yang belum dibaca dari lawan bicara tersebut).
  
- **Endpoint Get Chat Messages (Room Detail)**
  - `GET /api/chat/room/{room_id}/messages` atau `GET /api/chat/messages/{user_id_lawan}`
  - Fungsi: Mengambil riwayat pesan antara pengguna saat ini dengan pengguna lain. Otomatis mengubah status `is_read` pesan masuk menjadi `true` setelah diakses.
  - Response Data: List pesan (id, sender_id, text, timestamp).

- **Endpoint Send Message**
  - `POST /api/chat/send`
  - Body: `receiver_id`, `message`
  - Fungsi: Mengirim pesan ke pengguna lain. Jika room belum ada, backend membuatkan room baru.

- **Endpoint Unread Badges Summary**
  - `GET /api/chat/unread-summary`
  - Fungsi: Mengambil total keseluruhan pesan yang belum dibaca dari semua room, untuk ditampilkan sebagai badge di tab/navigasi bawah aplikasi.
  - Response Data: `total_unread_count` (integer).

Catatan untuk Frontend:
Nantinya frontend akan memilah list chat menjadi dua tab: "Semua" dan "Belum dibaca". Jika endpoint list chat bisa mengembalikan filter unread atau frontend yang memfilternya dari response list yang ada, mohon dipertimbangkan kemudahannya. Total unread messages (keseluruhan) akan dipasang di lencana Bottom Navigation.

## Request Perubahan Backend: Status Read pada Chat Messages (01-10-2026)

Berkaitan dengan fitur tampilan status pesan di chat room (centang terkirim & centang dibaca), diperlukan penyesuaian response API.

**Detail Request:**

### 1. Endpoint GET Messages — Pastikan Field `is_read` Konsisten
Endpoint `GET /api/chat/room/{room_id}/messages` dan `GET /api/chat/messages/{user_id_lawan}` wajib mengembalikan field `is_read` dengan tipe **integer** (bukan boolean):
- `0` = Pesan belum dibaca oleh penerima
- `1` = Pesan sudah dibaca oleh penerima

*Catatan: Saat ini response kadang mengembalikan boolean `true/false`. Frontend sudah handle keduanya, namun agar konsisten mohon standardkan ke integer.*

### 2. Endpoint `GET /api/chat/rooms` — Tambahkan Field `is_read` di Last Message
Untuk menampilkan status read/centang di **list inbox** (bukan hanya di dalam room), mohon tambahkan field `is_read_last` (integer 0/1) di object room:

```json
{
    "room_id": 1,
    "last_message": "Apakah barang masih ready?",
    "updated_at": "2026-10-01T08:00:00.000000Z",
    "unread_count": 2,
    "is_read_last": 0,
    "user": { ... }
}
```

*Keterangan: `is_read_last` menandai apakah pesan terakhir dari current user sudah dibaca oleh lawan bicara. Jika pesan terakhir bukan milik current user, nilai ini tidak relevan (bisa diisi `1`).*

Frontend akan menggunakan field ini untuk menampilkan ikon centang di preview pesan terakhir di list inbox.
